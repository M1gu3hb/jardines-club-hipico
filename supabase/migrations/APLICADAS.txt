# Lo que la base dice que se ha aplicado — y por qué este archivo existe
#
# `supabase db push` compara el PREFIJO del nombre de archivo con
# `supabase_migrations.schema_migrations.version`. Cualquier archivo cuyo prefijo no esté ahí lo
# considera PENDIENTE y lo ejecuta.
#
# Durante meses 16 de los 25 archivos tuvieron prefijos redondos inventados (…220000, …221000)
# que no correspondían a ninguna versión registrada. Consecuencia, comprobada leyendo el
# contenido de las migraciones implicadas:
#
#   `supabase db push` habría reejecutado sec_11 … sec_25 en orden de archivo:
#     · sec_13:75  →  `grant insert on jardines.solicitudes to anon` + `solicitudes_anon_ins`
#                     — reabre el alta pública sobre la tabla de leads;
#     · sec_20:9   →  lee `staff_token`, columna que ese mismo archivo borra en :79 y que hoy NO
#                     existe  →  el push ABORTA ahí;
#     · sec_21     →  que es justamente la que retira ese INSERT, NO llega a ejecutarse.
#
#   Resultado: `anon` con INSERT sobre `solicitudes` y las migraciones 21-25 sin reaplicar, a
#   partir del comando de despliegue estándar.
#
# ARREGLO: se renombraron los 16 archivos a su versión registrada (`git mv`, sin tocar una sola
# línea de SQL). El ledger es la fuente de verdad de qué corrió; el nombre del archivo solo tiene
# que coincidir con él. Renombrar NO es reescribir una migración aplicada — su contenido es
# idéntico— y las versiones registradas conservan el orden sec_01 … sec_25.
#
# Este archivo es la copia del ledger que el contrato `1.1` compara contra los nombres de
# archivo, para que la divergencia no pueda volver en silencio. Si aplicas una migración nueva,
# añade aquí su versión.
#
# ─────────────────────────────────────────────────────────────────────────────
# ⚠️ ESTE PROYECTO NO SE PUEDE RECONSTRUIR DESDE CERO. Las 19 migraciones que CREARON la base
#    —`jardines_01_schema_expose` … `jardines_11_staff_invitacion_rsvp` y `operativo_01` …
#    `operativo_09`— están en el ledger y **no existen como archivo en este repositorio**. Un
#    `db push` contra una base vacía fallaría en `sec_01`, que ya da por hechas las tablas.
#    Recuperarlas exige volcar el esquema de producción, y ese volcado incluiría el schema
#    `public` de Vero Seguros, así que no es una operación que se pueda hacer sin su visto bueno.
#    Está anotado como deuda; no se resuelve aquí.
